# gemini-gem/ — нотатки для себе (не для Gemini Gem, не для аплоаду)

Це службовий файл для Claude на майбутнє, коли доведеться повертатись до цієї папки. Не завантажувати в Gemini Gem.

Проєкт спочатку готувався під OpenAI Custom GPT (ліміт 20 файлів), потім користувач перейшов на **Gemini Gems**, у яких ліміт Knowledge — **10 файлів** (100 МБ кожен). Тому папку перейменовано з `gpt/` на `gemini-gem/`, а 24 сторінки об'єднано щільніше — не по 2, а по 2–4 в одному файлі.

## Що тут є

- `instructions.md` — системні інструкції для Gemini Gem (поле Instructions у конфігурації Gem).
- `description.md` — короткий публічний опис (поле Description, ліміт **300 символів**, вже перевірено).
- `pages/*.md` — knowledge-файли, кожен об'єднує кілька споріднених сторінок Hotel OS. Завантажуються в Gem як Knowledge files.

## Ліміт файлів

Gemini Gems дозволяють максимум **10 файлів** у Knowledge (по 100 МБ кожен). Зараз у `pages/` рівно 10 — ліміт вичерпано. Якщо треба додати щось нове, дописуй у вже наявний тематичний файл, а не створюй 11-й.

## Що об'єднано (і чому)

Було по одному файлу на кожну з 24 сторінок проєкту, потім об'єднано (і повторно об'єднано під ліміт 10) по темі. Кожен файл має один `##`-розділ на кожну вихідну сторінку:

- `overview.md` — головна маркетингова сторінка (`index`) + Dashboard (`dashboard`)
- `booking.md` — публічне бронювання (`book`), деталі бронювання (`booking`), нове бронювання (`new-booking`), підтвердження для гостя (`confirmation`) — увесь цикл бронювання, 4 сторінки
- `calendar-rooms.md` — календар (`calendar`) + номери (`rooms`)
- `housekeeping-ai-automations.md` — прибирання (`housekeeping`), AI-помічник (`ai`), автоматизації (`automations`) — 3 сторінки
- `guest-guests.md` — профіль одного гостя (`guest`) + список гостей/CRM (`guests`)
- `messages-notifications-search.md` — повідомлення (`messages`), сповіщення (`notifications`), пошук (`search`) — 3 сторінки
- `payments-sales.md` — оплати (`payments`) + продажі/аналітика (`sales`)
- `profile-settings.md` — особистий профіль співробітника (`profile`) + налаштування готелю (`settings`)
- `login-team.md` — вхід/автентифікація (`login`) + команда (`team`)
- `legal.md` — cookies (`cookies`) + конфіденційність (`privacy`)

24 вихідні сторінки / 10 файлів. Якщо ліміт колись підвищать (або переносите на платформу без обмеження) — можна розбити назад по одній сторінці на файл, контент для цього не втрачено, просто скопійований у більші файли.

## Структура кожного розділу всередині pages/*.md

Кожен `##`-розділ сторінки: `### Призначення` / `### Хто використовує` / `### Що можна робити` / `### Обмеження` / `### Прямі посилання` (що НЕ підтримується — саме на розділ "Обмеження" бот спирається, щоб зрозуміти, коли пропонувати "подати фідбек").

## Прямі посилання (deep-links з хешем)

Gemini не робить голий шлях типу `/rooms/` клікабельним — користувачу довелося б вручну вводити його в адресний рядок. Тому кожній сторінці в реальному HTML (`<page>/index.html`, або в `.js`-рендерері, якщо контент генерується динамічно — напр. `confirmation/confirmation.js`, `settings/settings.js`) додано `id="..."` на контейнери ключових секцій, а в кожному `##`-розділі pages/*.md є розділ `### Прямі посилання` зі списком готових markdown-посилань виду `https://hotelos.webart.work/<сторінка>/#<якір>` — вони не просто відкривають сторінку, а прокручують одразу до потрібного блоку.

Важливий виняток: `settings/index.html` рендерить лише одну активну секцію за раз (JS-таби), тому статичних `id` там недостатньо — в `settings.js` додано невеликий hash-роутер (`HASH_TO_SECTION` + `initFromHash()`), який при завантаженні сторінки з хешем типу `#payments` одразу перемикає на потрібну секцію налаштувань. Це єдине місце, де для deep-link довелося змінити логіку, а не лише додати `id`.

`instructions.md` вимагає, щоб бот завжди давав повний клікабельний markdown-посилання з цих списків (копіюючи дослівно), а не голий шлях і не вигаданий якір.

## Джерело даних

Усі описи написані на основі реального читання `index.html` + відповідного `.js`/`.css` кожної сторінки проєкту (не вигадано). Якщо продукт зміниться — файли в `pages/` та `id`-якорі в HTML/JS треба оновити вручну, автоматичної синхронізації немає.
